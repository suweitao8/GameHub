# HTML 游戏快速投稿设计

> 状态：已确认，进入实现
> 日期：2026-08-09
> 范围：GameHub `/games/upload` 快速投稿体验与创建 API 默认值

## 目标

把 GameHub 投稿收敛为“选择一个 HTML 文件并提交”。投稿人不需要在首次上传时填写标题、分类、标签、简介、操作说明或封面；系统继续负责 HTML 安全检查、大小限制、账号配额、频率限制和审核状态。

## 现状问题

当前上传页把单文件投稿拆成六个可见步骤，并要求用户处理多项元数据、封面、运行预览和封面生成。对于已经准备好 HTML 文件的投稿人，这些字段和状态都是额外负担，也让“快速投稿”看起来像一个复杂的创作向导。

## 方案与取舍

采用“前端极简入口 + 后端可兼容默认值”的方案：

- 上传页只暴露文件选择、文件状态和提交按钮。
- 创建 API 将 `gamefile` 作为唯一必需业务输入；缺失的元数据由服务端补齐，旧客户端仍可继续提交完整元数据。
- 标题优先从 HTML `<title>` 推导，其次使用文件名去掉扩展名，最后使用“未命名游戏”；标题仍遵守现有长度和安全校验。
- 分类默认为 `other`，简介、操作说明和标签默认为空。
- 页面不再让用户上传或调整封面，但会尝试生成标题封面；封面生成失败不能阻断游戏投稿，列表已有的占位封面继续生效。
- 运行预览不再阻塞提交。服务端在实际创建时执行权威安全检查；现有预览接口保留，供其他客户端或后续功能使用。
- 已有游戏编辑页继续保留完整元数据编辑能力，投稿完成后可以补充和修改信息。

### 未采用的方案

1. 只改前端：界面看似简单，但 API 仍要求调用方伪造元数据，不能真正支持“只给 HTML”。
2. 快速投稿加高级设置：能兼顾完整编辑，但入口仍包含复杂表单和多状态，不符合快速投稿的目标。

## 用户流程

1. 用户打开 `/games/upload`。
2. 通过点击、拖拽或键盘 Enter/Space 选择一个 `.html`/`.htm` 文件。
3. 页面立即检查扩展名和 20MB 大小上限，展示文件名与大小；可移除或替换文件。
4. 用户点击“提交游戏”。按钮进入 loading/disabled 状态，页面显示上传与检查状态，防止重复提交。
5. 服务端完成文件内容、资源引用、导航/联网限制、配额和审核状态处理。
6. 成功后显示“已发布”或“等待审核”，并提供打开游戏链接；失败显示服务端返回的具体中文原因。

## 前端设计

`GameUploadComponent`：

- 删除可见步骤条、预览 iframe、标题/分类/标签/简介/操作说明字段、手动封面字段和封面操作区。
- 使用可聚焦的上传区域，覆盖点击、拖拽和 Enter/Space；拖拽悬停时有明确视觉反馈。
- 选中文件后显示文件名、格式和大小，并提供可访问的移除/替换操作。
- 文件未选择、文件非法、提交中、提交失败、提交成功均有明确状态；提交按钮在无文件或提交中禁用。
- 保留离开页面时对未提交文件的提示，但提交成功或提交进行中不再提示。
- 移除对上传页 `GamePreviewProbeService` 的依赖；保留服务文件和 `/preview` API，避免影响其他调用方。

`games-api.ts` 和 `GamesService`：

- 上传元数据改为可选，`create(file, metadata?)` 允许只传文件。
- `buildGameUploadFormData` 只在元数据存在时序列化字段，保持完整元数据调用方的既有字段顺序和封面兼容性。

## 后端设计

创建路由在现有 `gameFile` 中间件之后、创建校验之前补齐默认值：

- `title` 缺失或为空时，从上传文件内容的 `<title>`、文件名依次推导。
- `description`、`instructions`、`tags` 缺失时分别使用空字符串、空字符串和空标签数组。
- `category` 缺失时使用 `other`。
- 补齐后继续走现有 `gameCreateValidator`，不放宽标题、描述、标签的安全约束。
- 更新路由仍使用完整编辑契约，不因创建 API 简化而覆盖已有字段为 `undefined`。

OpenAPI 将创建请求的 `required` 列表改为只包含 `gamefile`，并说明默认元数据规则；更新请求保持现有语义。

## 错误处理与安全

- 客户端只做快速格式/大小反馈；服务端安全校验仍是最终依据。
- 不改变单 HTML 契约：拒绝 ZIP、多文件、外链、联网、顶层跳转、危险 API、路径穿越和超过大小上限的文件。
- 不改变认证、限流、每账号游戏数、存储配额和审核状态逻辑。
- 自动封面是非关键辅助步骤；无法生成封面时仍提交游戏，让已有占位封面承接展示。

## 验证计划

- 客户端 API 契约测试：只传文件时 `FormData` 只包含 `gamefile`；完整元数据和封面序列化保持兼容。
- 服务端游戏 API 测试：认证用户仅提交 `gamefile` 可以创建，标题默认值和空元数据正确；现有完整元数据上传继续通过。
- 更新静态 GameHub 验证脚本，使其检查快速投稿入口和无复杂字段，而不是旧的预览/封面流程。
- 运行 `pnpm run build:server`、`pnpm run build:client`、相关 lint、OpenAPI 校验和 `pnpm run self-test:gamehub`。
- 启动从 `develop` 工作区提供的服务，使用真实浏览器验证 `/games/upload` 的文件选择、拖拽/键盘入口、提交 loading、成功/失败反馈和移动端布局。

## 不在本次范围

- 不重构游戏编辑页、审核页或运行时安全模型。
- 不增加 ZIP/多文件资源包支持。
- 不删除现有预览服务和预览 API。
